# The 10053 reader: plan

Written 2026-11-11. The format and the lab measurements are in `docs/trace-format-10053.md` (research of
2026-11-10). The decisions below were settled with the user on 2026-11-11 in a question-by-question review
(33 questions); the build is done and they are in `docs/DESIGN.md` § The 10053 reader. What was built, and where it
differs from this plan, is under "The build" and in the Log.

## Why

A 10053 trace is the optimizer's log of one hard parse: the statistics it read, the estimates it derived, the
transformations and join orders it weighed. It is hard to read as it comes: 18,523 lines for a two-table
statement with two subqueries, 93,620 for a ten-table join, no index, the same query block costed up to nine
times, every parameter printed twice. The tools that existed are a Windows tree viewer written for 10g (Sloot
and van der Ende, 2010), the Lab128 viewer (its download page is gone) and text search.

The first version is a **reader**: it makes the file navigable and explains what its parts are. It does not
compute anything from the costs.

## Decisions

### Scope

- **A reader, named "10053"** in the UI (the view, the mark on a statement), the docs and the CLI.
- **Input: a file that holds only 10053 dumps** (at least one dump, no 10046 record). This is how the traces
  arrive: taken separately for one or a few statements after a 10046 trace pointed at them.
- **A file with 10046 and 10053 interleaved is not read as 10053 in this version.** It opens as a 10046 trace
  as today. Two things change: the dumps' lines are no longer counted as unknown lines, and the trace facts
  carry a note ("2 optimizer (10053) dumps in this file, lines 54-18358 and 18734-27979; not shown as 10053
  yet").
- **19c is the tested version.** A file of another version opens best effort; the view's header says "read
  with the 19c rules; this file is 23.6" and the outline shows how many lines fell outside any known section.
- **Not in this version**: producing the trace from the app (turning the event on, `DBMS_SQLDIAG.DUMP_TRACE`);
  the assistant and `mtkprof mcp` (they do not open 10053 files); Compare and Cut on a 10053 tab.

### The view

A new view of its own, not a mode of the Lines view: the outline on the left, the text in the centre, the
guide on the right. Its look is agreed on a mock-up before the build (`docs/mockups/10053-reader/`).

- **Outline**, full depth, in file order: dump → phase (environment, transformations, costing, result) → section →
  iteration of a cost-based search → costing run → table / join order → join step. A node shows its line count; a
  join order node shows its own text from the trace (the tables, "aborted" or its cost). The plan's first idea was a
  level of query blocks above the costing runs (query block → costing run). It was not built: the outline follows the
  text, and a query block is costed once per iteration that holds it, so its runs are not adjacent in the file (nine
  runs of `SEL$1BA63A14` in `opt_subq_binds`). The level is the iteration of the cost-based search instead; a run
  stands under the iteration that costed it, with its query block in its label, and an *All | Runs* switch lists the
  runs alone, in file order, with their verdicts (decided on the
  mock-up, below).
- **Several dumps in a file**: the outline's top level lists them (sql_id, the first words of the SQL, the
  tables, line count, plan hash); one is open at a time. Two dumps of one sql_id are two entries, numbered in
  file order.
- **Centre: Formatted, with a Raw toggle.** Formatted is the trace's own lines in file order, dressed: banners
  become headings, landmarks are tinted, noise is folded, one-line SQL is pretty-printed, the plan table can
  show as a plan. Raw is the file untouched. Nothing is re-rendered as tables of numbers.
- **Noise folded by default**, each fold with its line count: the parameters with default values, the fix
  controls, the second parameter dump (`Optimizer state dump`), the adaptive plan's re-costing, repeated
  statement text.
- **Landmarks**: key lines marked in the text and listed, with next / previous keys: `Best:: AccessPath`,
  `Best:: JoinMethod`, `Final cost for query block`, `Join order aborted`, a bypassed or refused
  transformation, `Updated best state` / `Not update best state`, a hint with an error. The list was settled on
  the mock-up (below).
- **Costing runs**: each run shows the verdict the trace gives it and the run that produced the final plan is
  labelled. A run whose text equals an earlier one (addresses ignored) is marked "same as run N" and folded.
  This compares text; it does not read the numbers.
- **SQL**: every `UNPARSED QUERY IS` statement pretty-printed with the app's SQL formatter, with a diff against
  the previous version of the statement.
- **Final plan**: the dump's `Plan Table` in mtkprof's plan view (tree, predicates, query blocks), with "open
  in plan viz".
- **Guide**: fixed explanations per kind of section and line ("Access paths considered for this table; the
  line `Best::` is the one kept"), and a glossary of terms and codes as tooltips. An entry is written only when
  a named source (the trace's own legend, Oracle's documentation, Lewis, Breitling, Pagano) or the lab backs
  it; a section or term without one has no guide text. The sources are listed in the docs, not in the UI.
  Sentences about this trace's decisions, computed from its numbers, are not in this version.
- **Also**: notes and bookmarks on lines (desktop, as in the Trace pane, listed in Annotations); literal and
  regex search with the number of hits on each outline node; a where-am-I path above the text (dump › Costing
  › SEL$1BA63A14 run 3 of 9 › Join order 7 › Now joining MTK_CUST, each part a link); a line map beside the
  scroll bar (phases as bands, landmarks and hits as ticks, the visible range).
- **Confirmed by the owner on the mock-up, 2026-11-11** (`docs/mockups/10053-reader/`):
  1. **Landmark kinds on by default**: verdicts, final cost, best access path, best join method, aborted join orders
     and hint errors. Refusals (bypassed or refused transformations) are off by default: there is one line per
     transformation per query block, 190 in the mock-up's trace. A kind that is off is not tinted, not on the line map
     and not stepped through. The switches are kept.
  2. **The landmark list is a tab of the left panel** (Outline | Landmarks | Bookmarks), not a panel of its own.
  3. **Tints**: green for kept, grey for rejected or aborted, red for problems. Amber stays the selection and the
     search.
  4. **The SQL diff is against the previous statement in the file by default**, which is often another query
     block's text; a menu picks another earlier version.
  5. **The outline is in file order**, a run under the iteration that costed it, with an *All | Runs* switch (see
     the Outline bullet).

### Tabs and the link to a 10046 trace

- A 10053 file is **always its own tab** (desktop) or its own `serve` / report run. Given inside a set of 10046
  files it is left out of the set with a note.
- **A jump only**: a statement of a 10046 tab shows a "10053" mark when another open tab holds a dump with the
  same sql_id; the mark switches to that dump, and the dump links back. No data is joined. Desktop only (`serve`
  holds one session).

### Clients

| Client | What it has |
|---|---|
| Desktop, `mtkprof serve` | the view |
| Standalone HTML (`mtkprof html`, the default command) | the same view fed with the digest; where text is not included the centre says "1,234 lines not in this report (lines 2032-3265)" |
| Text (`mtkprof report`, the default command) | the digest |
| `mtkprof lint` | the 10053 line kinds and the dumps |

**The digest** is the trace without its noise, nothing computed. Per dump: sql_id and SQL, the altered
parameters and fix controls, the peeked binds, the outline with line numbers and line counts, the landmark
lines verbatim with their line numbers, each version of the transformed SQL pretty-printed, the final plan
with its predicates, the hints with their flags. `-redact-binds` and `-binds none` apply to the bind sections
(`Bind Info`, `Peeked Binds`) as they do to 10046 binds; literals in the SQL text and the predicates stay.

### Correctness

- **Best effort on what Oracle writes**: the format is undocumented free text that changes with releases; an
  unrecognized line stays readable where it is and is counted, and nothing is guaranteed for traces not seen.
- **Our own output is pinned**: every lab fixture has a committed outline and landmark list (a snapshot); a
  parser change that alters one shows in the diff. The 10046 golden tests do not change, for files with and
  without dumps.
- **Fixtures are real**, generated on the lab by `testdata/gen` (`sc_opt_*.sql`). The generator may create new
  objects in schema `MTK` (a partitioned table, a table without statistics): idempotent CREATE only, never
  DROP or TRUNCATE, as for the existing tables.

### Afterwards

Candidates without order or commitment, chosen after the reader has been used on real traces: a computed
summary per statement; decision views (transformation ledger, access paths per table, join order explorer);
the origin of a row estimate joined to the 10046 actual rows of the same plan; comparing two dumps; reading
the dumps of an interleaved file; a digest tool for the assistant and MCP; 21c and 23ai fixtures.

## Sequence

1. This plan and the format reference committed.
2. An interactive mock-up of the view on a real lab trace, light and dark, in `docs/mockups/10053-reader/`;

## The build

Done on 2026-11-11 in eight commits on `main` (the Log lists them). Where it matches the plan's list and where it
differs:

- **Fixtures**: eleven scenarios `sc_opt_*.sql`, not the plan's eight kinds: the plan's (a statement with
  subqueries and binds `opt_subq_binds`; two statements, one with a bad hint `opt_two`; an eight-table join by
  `explain plan` `opt_join8`; missing statistics with dynamic sampling `opt_nostats_ds`; a partitioned table
  `opt_part`; a parallel plan `opt_parallel`; three DML statements `opt_dml`; the interleaved file
  `opt_interleaved`) and three more: a `UNION ALL` with a `WITH` clause and OR expansion `opt_setop`, altered
  parameters with an `opt_param` hint `opt_altered`, and unified tracing `opt_unified`. The ten 10053-only traces are in
  `testdata/opt/19c/`, not `testdata/traces/19c/`; the interleaved one, with its tkprof output, is in
  `testdata/traces/19c/`.
- **Parser** (`internal/trace/dump.go`, `kind.go`): as planned, with a file kind (`FileKind10046`, `10053`, `Both`,
  `SniffFile`); a dump's lines are the line kind `optimizer`; inside a dump a valid 10046 record keeps its kind; the
  note for an interleaved file; `lint` reports the kinds and the dumps.
- **Model** (`internal/opt`, pure Go, streaming): as planned, plus the digest and the SQL pretty-printer (a port of
  the mock-up's, pinned by a golden file). Snapshots per fixture (outline, landmarks, text digest), a parity test
  against the mock-up's parser, prefix and mutation tests. About 290 MB/s, 24 MB of heap for a two-million-line dump.
- **Peek** (`internal/peek`): as planned (`Kind`, `OptDumps`, `OptSQLIDs`).
- **Engine**: **replaced by the Build contract below**. No routes for the outline, landmarks, pages or search: the
  document's `opt` field, two routes, `optSqlIds`. **No persisted outline**: the dumps are scanned from the file when
  the session opens; the cache format was bumped to 8 for the new line kind and the dump ranges of a 10046 file
  (`model.PersistVersion` 3), not for an outline.
- **Report**: the text digest, the digest in the document for the standalone HTML (and the engine's JSON and HTML
  exports), the redaction flags, as planned.
- **UI** (`web/src/lib/views/opt`, `data/opt*.ts`): the view, the guide and glossary data with their sources, the line
  map; the desktop's tab kind, the "10053" mark and jump, notes and bookmarks, the folder picker's tags, the
  Reports page, the standalone top bar. The plan's "persisted outline" and "routes" items have no counterpart.
- **Docs**: DESIGN, ARCHITECTURE, DESKTOP, HANDOFF, ROADMAP, MCP, the site's docs and index pages, README,
  `desktop/README.md`, a release notes draft (`docs/releases/next-10053.md`), this file and the format reference.
  The site is not published and no release is made.

## Build contract (what the Go side serves and the shells read)

Settled on 2026-11-11 after the first build wave, so the engine and the shells could be built at the same time.
It replaces "routes for the outline, the landmarks, pages of lines and search" above: a dump is megabytes, so
the client loads a dump's model and its whole text and searches in the browser.

- **The model**: `internal/opt/model.go` (`opt.File`, `opt.Dump`), mirrored by `web/src/lib/data/opt.ts`
  (`data/opt.test.ts` fails when the two drift).
- **A 10053 file** is a file with at least one dump and no 10046 record (`opt.File.Pure()`,
  `trace.FileKind10053`). It is always a session of its own. In a set of files it is left out with a note
  (`model.DropOptFiles`); of a set made only of 10053 files the first is opened and the others are named in a
  note.
- **The document** (`api/doc`, the JSON the standalone HTML embeds, `mtkprof json`) of a 10053 file is the
  ordinary document of an empty 10046 model plus one field:

  ```
  "opt": {
    "file":   opt.File,                       // always
    "digest": {                               // only in a document made for a client without a server
      "dumps": [opt.Dump, …],                 //   (mtkprof html, the default command, mtkprof json, the engine's HTML and JSON exports)
      "lines": [{"from": 32, "text": ["…", "…"]}, …]   // the digest's lines, runs of consecutive lines, ascending
    }
  }
  ```

  `opt` is absent for every other file. A shell that sees `doc.opt` shows the 10053 view and none of the 10046
  views. With `digest` it reads from the document; without, from the two routes below.
- **Routes** of a 10053 session (`serve`, and `/s/{id}/api/…` in the engine), both in `api/engine.openapi.yaml`:
  - `GET api/opt/dump?i=N` → `opt.Dump` as JSON (404 when the session is not a 10053 file or N is out of range).
  - `GET api/opt/text?i=N` → `text/plain; charset=utf-8`: the lines `viewFrom..viewTo` of dump N joined by
    `\n`, exactly `lineCount` lines, no `\r`.
- **The engine's session object** (`GET /engine/sessions`, the session events) gains `optSqlIds`: the distinct
  sql_ids of the session's dumps, present only for a 10053 session and only once it is ready. The desktop's "10053" mark on a statement
  of another tab reads it.
- **Redaction**: `-redact-binds` and `-binds none` act on `Dump.Binds[].value` and on the lines listed in
  `Dump.BindLines` (the text digest, the document's digest); a server's `api/opt/dump` and `api/opt/text` are the file as it is.
- **The text digest** is `opt.WriteDigest`; `mtkprof report` of a 10053 file prints it.
- **Refused for a 10053 file**: live follow of a local file (the engine: `follow: x.trc is a 10053 file (optimizer
  trace); it cannot be followed live: open it without follow`), the assistant, the brief, Compare, `mtkprof mcp`, the
  CSV export, and the CLI commands with nothing to show (`pivot`, `export`, `plan`, `refscript`, `ref`, `brief`,
  `compare`), each with one line.

What differs from the plan, and why:

- **Routes and persisted outline replaced** by the Build contract (above), settled after the first build wave so the
  engine and the shells could be built at the same time: a dump is megabytes, so the client loads a dump's model and
  its whole text once and searches and dresses it itself. The model of a 10053 file is not in the index cache;
  `CacheIndexFormat` 8 is for the `optimizer` line kind and the per-file dump ranges (`model.PersistVersion` 3).
- **Outline levels**: iteration of the cost-based search instead of query block above the runs, because a block's
  runs are not adjacent in the file (Decisions › The view).
- **Fixtures**: three scenarios more than planned (`opt_setop`, `opt_altered`, `opt_unified`); the 10053-only traces
  in `testdata/opt/19c/`.
- **Another version**: the count of lines outside any known section is in the information bar above the view, with
  "read with the 19c rules; this file is 23.6", not in the outline.
- **SQL diff**: the *Diff* button is off when a tab opens; switched on, it is against the previous statement in
  the file by default. The decision reads "by default"; the code does not show the diff until it is asked for
  (`views/opt/OptPanels.tsx`, `SqlUi.diff`).
- **The mark's jump** opens the first dump of the sql_id in the most recently used 10053 tab that has one; it does not
  select a line. The dump's "10046" link selects the statement in the Statements view of the most recently used 10046
  tab that has it.
- **A set**: from the folder picker a selection of 10046 and 10053 files opens as the 10046 set plus one tab for each
  10053 file (the plan: left out of the set with a note; that is what the engine does when the files arrive in one
  request without the picker, with a button beside the note that opens the file).
- **The assistant** in a 10053 tab is a panel that says it does not read optimizer traces, not an absent panel; the
  brief, Compare and the CSV export are disabled with the reason, Cut is not offered.
- **Redaction does not reach the view of a server**: `serve` and the desktop show the binds as they are in the file
  (the routes are raw, by the contract); `-redact-binds` and `-binds none` act on the text digest and on the
  document's digest (the standalone HTML, `mtkprof json`, the engine's exports).
- **Guide**: five section kinds have no entry (`col-usage`, `tsec`, `opt-metrics`, `qbreg-xml`, `hint-report`) and
  show "No guide text".
- **Found while writing the docs** (the code is as committed): the folder picker's *Open each in a tab* keeps *Follow*
  for a 10053 file, which the engine then refuses (`desktop/src/workspace/FolderPicker.tsx`, `openEach`); the picker's
  row tooltip lists the kind, not the sql_ids (the sql_ids are in the peek, not shown).
