# The I/O map, round 3: the density layer and the hot blocks — plan

Written 2026-11-08, the two follow-ups proposed at the end of the I/O map round (`docs/PLAN-IOMAP.md`) and approved by the user.
Above the marks limit (5,000 / 20,000 / 100,000) `/api/io/map` keeps every k-th wait, and a sample hides what a DBA looks for:
blocks read over and over (a cache too small for the working set, a multipass hash join re-reading its spill, a hot index root),
short bursts, the true density of a scan. The side panel's numbers counted the rows drawn ("≈ × k"), and a sample's distinct
blocks are not the trace's: every-k-th wait of a scan never continues the one before, so "sequential" read 0 % there.

## Decisions

- **Three engine answers, all over every matching wait** (the scope of `/api/io/map`: window, contexts, `stmt`, `event`):
  - `GET /api/io/density`: the waits counted into cells. The client sends its layout: the x segments (`xs=a.b.n,…`; I/O order:
    match indices, the slots of its order axis × the sampling step; time: its domain) and one `p=key:file.lo.hi.n,…` per panel
    (the panel's key selects the waits the way the view's panels do: `f<file>`, `o<obj>`, `t<file>`, `n<file>`, `rest`; the
    segments are the panel's y axis, linear or packed). A wait counts in every y cell its blocks touch (waits + 1, its blocks in
    the cell, µs × that share); x is its index (order) or its midpoint (time, clamped). Each cell has the event with the most waits.
    One pass with the layout given; without it a first pass finds the domain and the files (one panel per file).
  - `GET /api/io/hot`: block reads per block (a multiblock read counts each block), the most read blocks merged into runs of
    adjacent re-read blocks, and the exact per-object and per-(statement, file) numbers of the side panel.
  - `GET /api/io/map?reads=1`: each row also gets the reads of its most read block over the scope (the colour mode "re-reads").
  Added routes and an added optional field: no `engine.Protocol` bump; no persisted struct changes (no cache format bump).
- **Counting blocks in bounded memory, exact in practice.** A block's first read only sets it in a seen set (`blockSet`, chunks
  of 65,536 blocks of one file like a roaring bitmap: a sorted array of offsets up to 1,024, then an 8 KB bitmap; a full scan costs
  about a bit per block, scattered reads 2 bytes); only a block read again gets a counter. Above 1,000,000 counters the map is
  pruned the Misra-Gries way (the (cap/2 + 1)-th largest count is taken from all; a count is then low by at most the sum `dec`).
  The 65,536 most read blocks are merged into runs and recounted exactly in a second pass, so **every count shown is exact**; the
  answer says `exact: false` and a `bound` (a block in no run was read at most that often) when the prune ran or more blocks were
  re-read than are recounted. The seen set's cap (64 MB) and the per-object / per-statement distinct sets' cap (32 MB) are apart:
  the second only makes `distinct` approximate (`distinctExact`), never the hot list. Measured on a generated stream of 214 M
  block reads over 214 M distinct blocks (1.5 M full-scan reads, a spill read 25×, 1 M scattered reads): exact, 0.4 s, 98 MB peak
  heap; 4 M scattered reads over 1.4 M blocks (more re-read blocks than counters): pruned, the 2,000 hot blocks still exact, 85 MB.
- **A wait moves at most 65,536 blocks** (`MaxWaitBlocks`, all routes and the twins): a larger p3 is a corrupt line and must not make
  one wait cost a loop over millions of blocks. Counter keys hold files in [0, 2^31) and blocks in [0, 2^32); others are not counted.
- **Twins**: `data/iodensity.ts` (`ioDensityOf`), `data/iohot.ts` (`ioHotOf`), `data/blockset.ts` (`BlockSet`, `BlockCounter`,
  with the same byte model so a cap stops at the same wait), `ioMapOf(…, { reads })`; one shared case
  `web/src/lib/data/testdata/ioblocks-case.json` (an excerpt of io_waits.trc around stmt 22's spill, with caps small enough to
  prune), regenerated by `go test ./internal/analyze -run IOBlocksSharedCase -update-ioblocks-case`.
- **Runs**: adjacent blocks of one file each read twice or more; sorted by Σ re-reads (the reads a big enough cache would have
  saved: a multipass spill outranks a single hot block), or by the most reads of one block, or by time. Each run: reads, re-reads,
  min–max per block and the peak block, read and write waits, µs (each read's ela × its share of the read's blocks), first and last
  read, the top 3 objects (non-temp reads) and statements.
- **The density layer** (UI): drawn in each panel's canvas under the marks (after the grid and the extent bands), one slate hue
  (`--bm-dens`) whose alpha follows the cell's count on a square-root (default) or log scale against the largest cell of all
  panels; cells about 4 px square. Display › Density: **auto** (default: on while the marks are a sample), always, off; it counts
  waits (default), blocks or time; the marks can be hidden. A legend bar under the colour legend, a cell tooltip where no mark is
  hit (waits, blocks, time, the dominant event and its share, the block range, the order or time range). It follows the zoom (the
  request is the current layout; re-asked 200 ms after the layout rests) and the panels per object (their packed segments are the
  request's segments: a wait outside the sample's runs is outside the panel, as its mark would be).
- **Hot blocks** (UI): a side-panel tab: the runs with the object's name (`objnames.ts` and the name options; temp runs "temp
  segments"), file and block range, reads and re-reads, per block min–max, time, writes, first → last, the statements. A click
  zooms that panel's blocks to the run (with some context) and highlights its marks; the sort is a select. The header says how
  many distinct blocks were read and re-read, and whether the list is exact (else the bound).
- **Exact side panel**: the Objects tab (waits, time, blocks, distinct blocks read, re-read ×, sequential) and the Statements tab
  (reads per block per file) use `/api/io/hot` when it answers for the same scope; the sample's numbers remain the fallback.
- **Colour by re-reads**: six buckets of the reads of the mark's most read block (once, 2, 3–4, 5–8, 9–16, 17+) on a ramp
  `--bm-rr-*`; the map is asked with `reads=1` only in this mode.

## Batches

1. Engine: `IOEvents`, `blockSet` / `blockCounter`, `IOHotOn`, `IODensityOn`, `IOMapWith` reads; slice handlers, routes, parity
   queries; OpenAPI, contract test, `desktop/src/engine/api.d.ts`; the TS twins, the shared case, the density layout
   (`data/densitylayout.ts`), the re-reads colour mode and the density paint in `blocklayout.ts`. Tests; measured on `testdata/big`.
2. View: `BlockMap.tsx` (density layer, legend, tooltip, Display options; the Hot blocks tab; exact Objects and Statements tabs;
   the re-reads mode), CSS; screenshots light and dark at 1280 and 1600 px; the standalone report.
3. Docs (DESIGN, ARCHITECTURE, HANDOFF, DESKTOP, site), `make web`, CI, commit, push.
