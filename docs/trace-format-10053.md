# Oracle 19c optimizer trace (event 10053) — format reference

Verified against real 19.27 traces generated in the dbmint lab (schema `MTK`, session-level events, read-only
statements). The research probe of 2026-11-10 gave the first picture; the fixtures of 2026-11-11 checked it and
added the cases it lacked. The fixtures are in `testdata/opt/19c/` (ten files with 10053 dumps only) and
`testdata/traces/19c/opt_interleaved.trc` (10046 and 10053 together), generated by the scenarios
`testdata/gen/sc_opt_*.sql` (§ The scenarios). Excerpts below are quoted from them as `file:line`. Anything not seen
in a fixture is marked *(unverified)* with its source, or says that only the probe trace showed it. 21c and 23ai were
not generated.

mtkprof reads this format since 2026-11-11 (`docs/DESIGN.md` § The 10053 reader): a file with dumps and no 10046
record opens as a 10053 trace; a file with both opens as a 10046 trace with a note, and the dumps' lines are counted as
`optimizer` lines, not as unknown lines (`mtkprof lint` on `opt_interleaved.trc`: 27,007 `optimizer` lines, dumps at
lines 54-18356 and 18684-28072).

## What the trace is

The optimizer's log of **one hard parse**: one dump per optimized statement, written while the statement is
compiled. It has no `tim=` values and no per-line timestamps; it is a record of decisions, not of time. The one
exception is a `*** ` timestamp line before some steps of dynamic sampling (§ 7). A statement that finds a shareable
cursor writes nothing.

## How it is produced

| Command | Notes |
|---|---|
| `alter session set events '10053 trace name context forever, level 1'` / `... context off` | the classic event; used by nine of the ten 10053-only scenarios and by the interleaved one. Level 1 and level 2 gave the same output on 19.27 apart from ids in the probe (older sources say level 2 leaves the statistics out). |
| `alter session set events 'trace[rdbms.SQL_Optimizer.*]'` / `... off` | unified tracing, 11g+; the same format. `opt_unified.trc` holds the second statement of `opt_two.trc`: its dump has the same 9,385 lines as the second dump of `opt_two.trc`. `[sql:<sql_id>]` limits it to one statement *(unverified here; oracle-base.com)*; also `alter system` *(unverified; Jonathan Lewis, Oracle-L 2022)*. |
| `dbms_sqldiag.dump_trace(p_sql_id, p_child_number, p_component => 'Optimizer' \| 'Compiler', p_file_id)` | re-optimizes an existing cursor without running it; the environment comes from `V$SQL_OPTIMIZER_ENV`, so the result may differ from the original parse *(unverified here: the probe failed on a missing grant; Oracle Optimizer blog, Jonathan Lewis 2014)*. |
| `V$DIAG_OPT_TRACE_RECORDS`, `V$DIAG_TRACE_FILE_CONTENTS` (12.2+) | the same records as rows, with `SECTION_NAME`, `COMPONENT_NAME`, `RECORD_LEVEL` *(unverified; Oracle reference)*. |

`explain plan for …` is a hard parse and writes a dump (`opt_join8`, `opt_nostats_ds`, `opt_part`, `opt_setop`).

## Where a dump starts and ends

- Start: the first `Registered qb: … (PARSER)` line outside a dump. Nothing before it names the statement; the
  `sql_id` comes about 50 lines later in `----- Current SQL Statement for this session (sql_id=…) -----`. **A dump
  has several `(PARSER)` registrations**, one per query block of the statement as written, a few lines apart
  (`opt_subq_binds.trc` lines 32, 40, 47, 54: `SEL$1` to `SEL$4`); they are all part of the one dump. The first block
  is named after the statement type:

  ```
  opt_dml.trc:32    Registered qb: INS$1 0x4d6e66f0 (PARSER)
  opt_dml.trc:39    Registered qb: SEL$1 0x4d6e2970 (PARSER)
  opt_dml.trc:3611  Registered qb: UPD$1 0x4d6e66f0 (PARSER)
  opt_dml.trc:3618  Registered qb: SEL$1 0x4d6e2970 (PARSER)
  opt_dml.trc:3625  Registered qb: SEL$2 0x4ce03d08 (PARSER)
  opt_dml.trc:7845  Registered qb: DEL$1 0x4d6e66f0 (PARSER)
  ```

  `INS$1`, `UPD$1` and `DEL$1` open the dump of an `INSERT … SELECT`, an `UPDATE` and a `DELETE` (`opt_dml`: three
  dumps in one file); the subquery or source query follows as `SEL$n`. In a set operation `SET$1` is registered
  among the `SEL$n` blocks, after `SEL$6` and before `SEL$7` of a `UNION ALL` of two joins with a `WITH` clause:

  ```
  opt_setop.trc:71  Registered qb: SEL$6 0x6392adb8 (PARSER)
  opt_setop.trc:78  Registered qb: SET$1 0x63920db8 (PARSER)
  opt_setop.trc:85  Registered qb: SEL$7 0x63923900 (PARSER)
  ```

  `MRG$1` for `MERGE` *(unverified)*.
- End: `====================== END SQL Statement Dump ======================`. Lines follow it up to the next dump:
  the adaptive plan's execution lines, written at the first execution (`opt_two.trc:18279`):

  ```
  AP: qesdpDPCSetupNextExec(enter): SQL_ID=267mhyr5wydy6
  AP: qesdpDPCSetupNextExec: Setup Phase-0
  AP: qesdpDPCSetupNextExec(exit)
  ```

  They run from a few to a few hundred lines, up to the next dump: in `opt_dml.trc` the last of them
  (`AP: qesdpSetupMutable(enter): SQL_ID=419jcqfm9713k`, line 3610) is the line above the `Registered qb: UPD$1` that
  starts the next dump.
- The file prologue and the `*** ` markers are those of a 10046 trace (`docs/trace-format-19c.md`). In a file written
  by `trace[rdbms.SQL_Optimizer.*]` the prologue is the same (`opt_unified.trc` lines 1-30).
- **A PX slave of the statement writes its own trace file** with no dump of the coordinator's; the generator copies
  the slave files of `opt_parallel` to `out/` and logs how many dumps each holds, but keeps none of them, so no
  fixture shows a slave file *(unverified here)*.

### With event 10046 in the same file

Both events write to the process's trace file, so a session with both on gives one interleaved file
(`opt_interleaved.trc`, scenario `sc_opt_interleaved.sql`: `10046 … level 12`, then `10053`, two statements). Its
altered parameters show the 10046 side effect, `sqlstat_enabled = true` (`opt_interleaved.trc:181`, and again at
18811 for the second dump):

```
  PARAMETERS WITH ALTERED VALUES
  ******************************
Compilation Environment Dump
sqlstat_enabled                     = true
Bug Fix Control Environment
```

- **A statement with binds** (`inter_a`, `sqlid='3zjjnrf5a9vh7'`): `PARSING IN CURSOR` (line 45), its text,
  `END OF STMT`, `PARSE #…mis=1` (53), then the dump (54-18356), then `EXEC #…mis=1,…plh=2477488908` (18380). The
  optimization is deferred to the first execution, for bind peeking.
- **A statement without binds** (`inter_b`, `sqlid='8a01tvd45h89r'`): the dump comes first (18684-28072), then
  `PARSING IN CURSOR` (28074) and `PARSE #…mis=1,…plh=2572512466` (28081; the PARSE line is written when the call
  ends).
- **Recursive SQL inside the dump**: the optimizer's dictionary lookups appear as complete `dep=1` 10046 records
  between optimizer lines (`opt_interleaved.trc` lines 15597-15647: one cursor parsed at 15597 and executed twice,
  with `FETCH`, `STAT` and `CLOSE`). They are rule-based SYS statements and have no dump of their own.
- **Join keys**: the dump's `sql_id` is the cursor's `sqlid`; `plan_hash` in the dump's `Content of other_xml
  column` is the `plh` of the EXEC (or PARSE) line: 2477488908 at line 15902 against 18380, 2572512466 at 25647
  against 28081. The `plan_hash_value=-1817478388(93ab7b0c)` of the `Starting SQL statement dump` line is another
  hash.

## Sections, in file order

A banner is a line of `*`, `-` or `=` above and below a title; their lengths vary.

### 1. Parser query blocks

```
opt_subq_binds.trc:32
Registered qb: SEL$1 0x6554f888 (PARSER)
---------------------
QUERY BLOCK SIGNATURE
---------------------
  signature (): qb_name=SEL$1 nbfros=2 flg=0
    fro(0): flg=4 objn=108609 hint_alias="C"@"SEL$1"
    fro(1): flg=4 objn=108611 hint_alias="O"@"SEL$1"
```

`objn` is the object number (0 for an inline view or subquery). The same line shape registers every block a
transformation creates later, with the derivation in the parentheses:

```
opt_two.trc (dump 1)
Registered qb: SEL$58A6D7F6 0x… (VIEW MERGE SEL$2; SEL$1; SEL$2)
Registered qb: SEL$1BA63A14 0x… (SUBQUERY UNNEST SEL$58A6D7F6; SEL$4 SEL$3)
Registered qb: SEL$FDFFF663 0x… (PLACE GROUP BY SEL$1BA63A14; SEL$1BA63A14; LIST 1)
Registered qb: SEL$1BA63A14 0x… (COPY SEL$1BA63A14)
```

Derivations seen in `testdata/opt/19c/`, with the number of lines over its ten files: `PARSER` (42), `COPY` (25), `VIEW MERGE`
(16), `ELIMINATION OF GROUP BY` (16), `SPLIT/MERGE QUERY BLOCKS` (12), `QUERY BLOCK TABLES CHANGED` (12), `PLACE GROUP BY`
(12), `SUBQUERY UNNEST` (5), `OR EXPANSION UNION ALL BRANCH` (3), `PUSHED PREDICATE` (2), `MATERIALIZED WITH CLAUSE` (2).
The ones the probe did not show:

```
opt_setop.trc:1369  Registered qb: SEL$7471ABDD_2 0x638b8b98 (OR EXPANSION UNION ALL BRANCH SEL$7471ABDD)
opt_setop.trc:3011  Registered qb: SEL$C1A6B6D4_3 0x638b6ed8 (OR EXPANSION UNION ALL BRANCH SEL$C1A6B6D4)
opt_setop.trc:5920  Registered qb: SEL$BB173B6F 0x63866300 (MATERIALIZED WITH CLAUSE SEL$6; SEL$6)
opt_setop.trc:5928  Registered qb: SEL$BB173B70 0x63865200 (MATERIALIZED WITH CLAUSE SEL$6)
opt_two.trc:22844   Registered qb: SEL$B01C6807 0xfb98b418 (PUSHED PREDICATE SEL$3; SEL$5D4F31E4; "T"@"SEL$2" 3)
```

- A block made by OR expansion is named after its source with a **suffix**, `_2`, `_3`: `SEL$7471ABDD_2`.
- A block made by `PUSHED PREDICATE` carries a quoted alias with its query block in the parentheses
  (`"T"@"SEL$2" 3`).
- `MATERIALIZED WITH CLAUSE` registers two blocks for one `WITH` subquery; the second has the shorter parentheses.
  Between the two a `Copy query block qb# -1 (<unnamed>) : SELECT /*+ CACHE_TEMP_TABLE(T1) */ "C0", "C1" FROM
  "SYS"."SYS_TEMP_0FD9D6F67_2FDB69A" T1` line shows the temporary table.
- `PROJECTION VIEW FOR CVM` appears in the probe trace kept with the mock-up, not in a fixture
  (`docs/mockups/10053-reader/data/two.trc:20524`: `Registered qb: SEL$F2B2F603 0x6994c0 (PROJECTION VIEW FOR CVM
  SEL$2)`).

### 2. Preamble lines

`SPM: statement not found in SMB`, `SPM: capture of plan baseline is OFF`, `kkoctx(): choosing CBO since
optimizer mode set to all/first_rows`, the `Automatic degree of parallelism (AUTODOP)` banner with its reason
(`… is disabled: Parameter.`), a first `PM:` (predicate move-around) pass. `SPM: statement not found in SMB` is the
only plan baseline line in the fixtures: none has a baseline in use.

### 3. `OPTIMIZER INFORMATION`

- `----- Current SQL Statement for this session (sql_id=…) -----`, the statement text as typed, `----- Parser
  State -----` (four lines).
- `Legend`: the trace's own abbreviation list. Transformations: CBQT, JPPD, OJPPD, FPD, PM, CVM, SPJ, SJC, SU,
  OBYE, OST, ST, CNT, JE, JF, CBY, SLP, DP, VT, AAT, ORE, LORE. Terms: qb, LB, DK, LB/K, DB/K, CLUF, NDV, Resp,
  Card, Resc, NL, SM, HA, CPUSPEED, IOTFRSPEED, IOSEEKTIM, SREADTIM, MREADTIM, MBRC, MAXTHR, SLAVETHR, dmeth (with
  its ten codes), sel, ptn, AP. Prefixes used but not in the legend: TE (table expansion), BJ (bushy join), PJE,
  OJE, CSE (common subexpression elimination, by its banner), GBP (group-by placement), SPD (SQL plan
  directives), CBRID, and UPT (`Checking validity of unpivot transformation`), SQE (`Trying SQ elimination`),
  SQT (`Considering Statistic-based Query Transformation`), DCL (`Checking validity of group-by elimination`).
- `PARAMETERS USED BY THE OPTIMIZER`:
  - `PARAMETERS WITH ALTERED VALUES`, then `Compilation Environment Dump` (`name = value` lines, empty when
    nothing is altered) and `Bug Fix Control Environment` (altered fix controls; empty in all fixtures).
  - `PARAMETERS WITH DEFAULT VALUES`, then `Compilation Environment Dump` (about 610 lines such as
    `optimizer_features_enable           = 19.1.0`, hidden parameters included). The fix controls are not
    listed here: the full list is in the `Optimizer state dump` (section 9).
  - `PARAMETERS IN OPT_PARAM HINT` (empty without such a hint).
- `Column Usage Monitoring is ON: tracking level = 53`.

The altered and `OPT_PARAM` sections with something in them (`opt_altered.trc`, after `alter session set
optimizer_index_cost_adj = 50`, `optimizer_mode = first_rows_10`, `"_optimizer_cost_based_transformation" = off` and a
statement with `/*+ opt_param('optimizer_index_caching' 40) */`):

```
opt_altered.trc:155
  *************************************
  PARAMETERS WITH ALTERED VALUES
  ******************************
Compilation Environment Dump
optimizer_mode                      = first_rows_10
optimizer_index_cost_adj            = 50
_optimizer_cost_based_transformation = off
Bug Fix Control Environment


  *************************************
  PARAMETERS WITH DEFAULT VALUES
  …
opt_altered.trc:780
  ***************************************
  PARAMETERS IN OPT_PARAM HINT
  ****************************
  optimizer_index_caching             = 40
***************************************
Column Usage Monitoring is ON: tracking level = 53
```

In the altered section a name is printed in the order of the session, the `=` is not aligned for a long name, and the
section ends at `Bug Fix Control Environment`. Without altered parameters the two headers follow each other
(`opt_subq_binds.trc:158-159`).

### 4. Query transformations

```
Considering Query Transformations on query block SEL$2 (#0)
**************************
Query transformations (QT)
**************************
JF: Bypassed: not a UNION or UNION-ALL query block.
ST: not valid since star transformation parameter is FALSE
TE: Bypassed: No partitioned table in query block.
ORE: bypassed - No valid predicate for OR expansion.
VT: Bypassed: inmemory is disabled.
JE:[V2]: Cannot eliminate C by ref. join elim - predicate column refs.
SU:   Checking validity of unnesting subquery SEL$3 (#3)
SU:   Passed validity checks, no costing.
```

One line per step: a prefix (the transformation), a colon, free text. The wording of a refusal is not uniform
(`Bypassed:`, `bypassed -`, `not valid since`, `Cannot …`, `invalid because …`). After a transformation the
statement is printed again as one line (up to 1,111 characters in the probe):

```
******* UNPARSED QUERY IS *******
SELECT "C"."NAME" "NAME","O"."STATUS" "STATUS",SUM("O"."AMOUNT") "AMT" FROM "MTK"."MTK_CUST" "C", …
```

Other headers of this phase: `SQL:******* UNPARSED QUERY IS *******` (the commonest, 111 of the 269 in the ten
fixtures), `Stmt: ******* UNPARSED QUERY IS *******`, `BEFORE REDUCTION` / `AFTER REDUCTION`, `QB before group-by
removal:` and the like, `Final query after transformations:******* UNPARSED QUERY IS *******`.

**OR expansion** (`opt_setop.trc`, a `UNION ALL` whose branches have `OR` predicates). Where it does not apply, one
line (`opt_setop.trc:835`: `ORE: bypassed - No valid predicate for OR expansion.`). Where it applies, `ORE:` lines
check the predicate chains, then the cost-based search starts, once before and once after subquery unnesting:

```
opt_setop.trc:1304  ORE: Trying CBQT OR expansion before unnesting
opt_setop.trc:1367  ORE: Switching to two pass because of # conjunction: 2
opt_setop.trc:1368  ORE: Starting iteration 1, state space = [{ 1 2 }]
opt_setop.trc:1378  ORE: Transformed query
opt_setop.trc:1388  ORE: Costing transformed query.
…
opt_setop.trc:3009  ORE: Updated best state, Cost = 619.148457
opt_setop.trc:3010  ORE: Starting iteration 2, state space = [{ 1 }]
…
opt_setop.trc:3388  ORE: Not update best state, Cost = 709.783197
opt_setop.trc:3643  ORE: Trying CBQT OR expansion after unnesting
```

The state space is written `[{ 1 2 }]`, not `(1,2,3,4) : (0,0,0,0)` as for `GBP`. `Starting iteration 1` is written twice (lines 1368 and 2084) before the first verdict (line 3009): the search for
the branch blocks (`SEL$7471ABDD_2`, `SEL$C1A6B6D4_2`) runs inside it. `LORE:` lines (line 1546: `LORE: Or-Expansion
validity checks failed on query block SEL$6 (#3) because Cost based OR expansion enabled`) belong to the same group.

The bind block has the shape of a 10046 `BINDS` block (the 10046 classifier already takes these lines for bind
lines). `SPD: BEGIN context at statement level` … `SPD: END context at statement level` lists the objects and
their SQL plan directives (`dirid = …, state = 1, flags = 1, loc = 1, forDS = NO, forCG = YES {E(108611)[1]}`).

### 6. Cost-based transformations

A state-space search: each iteration costs one variant of the statement and ends in a verdict.

```
GBP: Starting iteration 1, state space = (1,2,3,4) : (0,0,0,0)
GBP: Costing transformed query.
…one or more costing runs (section 7)…
GBP: Updated best state, Cost = 384.608830
GBP: Starting iteration 2, state space = (1,2,3,4) : (C,0,C,C)
…
GBP: Not update best state, Cost = 385.608830
```

Seen with the prefixes `GBP`, `CVM`, `JPPD` (`JPPD: Will not use JPPD from query block SEL$1 (#1)`, `CVM: Will
not merge view SEL$2 (#2)`) and `ORE` (§ 4). Between iterations: `CBQT: Looking for cost annotations for query block …, key =
…`, `CBQT: Saved costed qb# 2 (…)`. **Searches nest**: in the hinted probe statement the JPPD iterations 1 and
2 run inside CVM iteration 2, and a second JPPD search follows the CVM verdict; in `opt_setop.trc` iteration 1 of `ORE`
holds another iteration 1. A run can be ten lines long
when its cost is reused (`CBQT: Replaced cost annotations`).
A parse-time line per step, `TIMER: SU: iteration (#1) SEL$… cpu: 105.656 sec elapsed: 110.375 sec`, exists
from 12.1.0.2 under fix control 16923858 *(unverified; Franck Pachot, dbi-services)*.

`optimizer_dynamic_sampling = 4`). **Timestamp lines appear inside the dump here, and only here**: a
`*** <ISO time> (PDB1(3))` line, preceded by a blank line, before the initial checks, the generated query and the
executed query (20 of them in the file; every other fixture has the one before the dump):


## Not verified

- 21c and 23ai. A 23.6 excerpt shows the 19c bind section unchanged (Jonathan Lewis, 2025).
- Star transformation (every dump says `ST: not valid since star transformation parameter is FALSE`) and SQL plan
  baselines in use (`SPM: statement not found in SMB` only); `MERGE` statements (`MRG$1`).
- `DBMS_SQLDIAG.DUMP_TRACE` output and `[sql:<sql_id>]` filtering.
- A dump cut by `max_dump_file_size`, and a session whose trace continues in another file.
- Whether a PX slave trace file holds a dump: the generator does not keep them.

## The scenarios

`testdata/gen/sc_opt_*.sql`, one per fixture, run by `testdata/gen/run_gen.sh` on the lab (`opt` runs all eleven;
`opt_two opt_part` runs those by name; the `dbmint-oracle-test` skill has the connection details). Each sets the
trace file identifier (`_prologue.sql`: `mtk_<scenario>`), runs `_opt_tag.sql` before the event is turned on, and puts
the tag in a comment of every traced statement (`/* mtk_opt_&TAG two_a */`; month, day, `t`, time to the
millisecond), so the statement is a new `sql_id` and a hard parse on every run. The events are session-level; the
scenarios create objects in schema `MTK` only (`01_schema.sql`: `MTK_NOSTATS`, `MTK_PART`, `MTK_PX_BIG`,
`MTK_DML_SRC`, `MTK_DML_TGT`, `MTK_DML_SCRATCH`; `CREATE` only, never `DROP` or `TRUNCATE`).

| Scenario | Fixture | Event |
|---|---|---|
| `sc_opt_subq_binds` | `opt_subq_binds.trc` | 10053 level 1 |
| `sc_opt_two` | `opt_two.trc` | 10053 level 1 |
| `sc_opt_join8` | `opt_join8.trc` | 10053 level 1, `explain plan for` |
| `sc_opt_nostats_ds` | `opt_nostats_ds.trc` | 10053 level 1, `optimizer_dynamic_sampling = 4` |
| `sc_opt_part` | `opt_part.trc` | 10053 level 1, `explain plan for` |
| `sc_opt_parallel` | `opt_parallel.trc` | 10053 level 1, parallel query enabled |
| `sc_opt_dml` | `opt_dml.trc` | 10053 level 1, each DML rolled back |
| `sc_opt_setop` | `opt_setop.trc` | 10053 level 1, `explain plan for` |
| `sc_opt_altered` | `opt_altered.trc` | 10053 level 1, three altered parameters |
| `sc_opt_unified` | `opt_unified.trc` | `trace[rdbms.SQL_Optimizer.*]` |
| `sc_opt_interleaved` | `opt_interleaved.trc` (with tkprof output) | 10046 level 12 and 10053 level 1 |

The script writes `out/<scenario>.trc` next to itself on the lab host (`OUT`, default `testdata/gen/out`); the
interleaved scenario also gets `out/<scenario>.tkprof.txt` and `.tkprof-noagg.txt`. Copying to the repository is done
by hand: the ten 10053-only traces go to `testdata/opt/19c/`, `opt_interleaved.trc` and its two tkprof files to
`testdata/traces/19c/`. A regenerated fixture has new `sql_id`s and new addresses, so the snapshots of
`internal/opt` change (`go test ./internal/opt -run Snapshot -update`, then read the diff).
