Oracle SQL trace · 19c, 21c, 23ai

The modern 10046 trace analyzer.

tkprof sums a trace and throws the rest away. mtkprof keeps all of it and shows where the response time went: by statement, by execution, by second. The same numbers as tkprof, exactly, and everything tkprof leaves out.

Why modern

tkprof gives you totals. Tuning needs the rest.

tkprof's numbers are still the reference, so mtkprof reproduces them and is tested against them. Everything else is new.

Three ways to run it

Same engine, from a terminal on the database host to a desktop app.

The parser, the model and the numbers are the same everywhere. Pick the surface that fits where the trace is.

Command line

Copy the binary next to the trace, like tkprof. A text report with the resource profile, statements ranked by response time, executions with their binds, plans and findings. Plus pivots, CSV export and a before/after compare.

$ mtkprof report trace.trc -top 20
$ mtkprof pivot trace.trc -by event
$ mtkprof compare a.trc b.trc

For: the database host, scripts, tickets.

Browser

A self-contained HTML file you can mail to a colleague, or the same UI served from the binary. Overview, Statements, Waits, Timeline, Sessions and Pivot, all following one time window and one session filter.

$ mtkprof html trace.trc
$ mtkprof serve trace.trc
  http://127.0.0.1:8046/

For: exploring one trace, sharing a finding.

Desktop app

Traces in tabs that reopen in a second from an index cache. The raw trace lines, notes and bookmarks, saved pivots, and connections that fetch or follow traces over ssh or straight from the database.

$ mtkprof open trace.trc
  # or double-click a .trc file
  # Windows · macOS · Linux

For: daily tuning work across many traces.

What you get

The whole trace as a model you can slice.

A trace becomes statements, cursors, calls, waits, binds, plans, sessions and time. Every view reads that one model, so a number in one place is the same number everywhere else.

Statements, down to the execution

Statements are ranked by response time including their recursive children and the idle time between their calls. Open one to see where its time went.

  • Its own resource profile, waits by event and object, with the line in the trace
  • tkprof-style call table, exclusive or inclusive of recursive SQL
  • Every EXEC with its fetches, rows and bind values; tick two to compare them
  • Row-source plans from the STAT lines, one per plan hash, hot steps marked

Time is a filter

The timeline shows every call of every statement. Drag to pick a window and every view follows it: profile, statements, waits, pivot. Click a block to window it; jump from the window to its lines in the raw trace.

  • Lanes colored by call phase, by wait event or by class
  • Session, module, action and client id filters, trcsess merges included
  • Findings with their evidence: outlier executions, hard parsing, small fetches, a commit per row, client think time

Pivot anything

Pick calls or waits, group by one or two dimensions (statement, wait event, object, plan hash, module, action, session, time bucket…), choose the measures and download the result as CSV. mtkprof pivot does the same group-by on the command line, up to four dimensions.

Many files, one trace

Pass any number of files and directories. Split traces are stitched back together, independent sessions sit side by side, and parallel-query slave traces are attached to their query coordinator.

  • Response time is the sum over sessions, not the wall clock
  • A Files panel scopes every view to some of the files
  • mtkprof compare a.trc b.trc: statements matched by sql_id, ranked by how much they changed

Big traces

A 10 GB trace on a laptop.

By default the whole model is kept in memory, which is fast and fine up to a gigabyte or two. Above that, pick a mode: the numbers stay the same, only what is kept changes.

ModeWhat it keepsMeasured
defaulteverything: calls, waits, binds, drill-down1 GB trace: about 7 s and 2 GB of memory for the HTML report
-lowmemeverything except bind valuesevery other number identical
serve -facts=falsemodel on the server; the browser asks for group-bys and details118 MB trace: browser loads a few hundred kB
serve -spillcalls, waits and binds in temp files about the size of the trace; full drill-down1 GB trace: 66 MB RSS, Pivot in about 0.3 s
-aggregateaggregates only: profiles, statements, sessions, findings10 GB trace: about 0.5 GB, 32 s

mtkprof desktop

A workbench for every trace you open.

The desktop app is a small native shell around the mtkprof engine. It runs on your machine, holds several traces at once and remembers them: open a trace you looked at last week and it is back in about a second, with your notes.

Tabs and an index cache

Open files, folders or a pasted path; drop them on the window; double-click a .trc. Parsed traces are kept by content, so a renamed copy opens from the cache too.

Lines

The raw trace, paged, with line kinds colored, the selected statement marked in the gutter, streaming search and jump to time. Every "line N" in the views opens it.

Notes and bookmarks

Annotate a statement, an execution, a time window or a line. Notes belong to the trace's content, not its path, and export to Markdown or JSON.

Fetch over ssh

Browse the trace directories on a host, fetch with gzip and resume, or follow a growing trace as a live tab. Uses your ~/.ssh/config, agent and bastions.

Straight from the database

List sessions and switch SQL trace on and off, fetch trace files from the ADR, and pull object names and plans for the trace. No OS access needed.

No secrets at rest

Connections have no password field. Passwords and passphrases are asked when used and kept only in the engine's memory until the app quits.

Library and reports

Save pivot configurations and apply them to any trace. Save the text, JSON, CSV or standalone HTML report of a tab.

Windows, macOS, Linux

Installers for Windows 10/11 x64, macOS on Apple Silicon and Intel, and Linux x64 as AppImage or .deb.

Get started

Trace a session, then read it.

Download the binary for your platform from the releases page (or build it with Go). There is nothing to install and no database connection is needed to analyze a trace.

  1. Switch on SQL trace

    With waits, binds and row-source statistics for every execution.

    alter session set tracefile_identifier = 'mytest';
alter session set events 'sql_trace
  wait=true, bind=true,
  plan_stat=all_executions';
-- ... run the workload ...
alter session set events 'sql_trace off';

  2. Find the file

    It is in the diagnostic destination of the instance.

    select value from v$diag_info
 where name = 'Default Trace File';

  3. Run mtkprof on it

    The text report and the HTML report land next to the trace.

    $ mtkprof cdb1_ora_4711_mytest.trc
$ open cdb1_ora_4711_mytest.trc.html
